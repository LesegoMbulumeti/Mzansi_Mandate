# Setup and teamwork guide

## 1. Backend framework and database choices

| Concern | Choice | Why for a 12-hour build |
|---|---|---|
| Web framework | **FastAPI** | Async (fits the XRPL websocket client), automatic OpenAPI docs your React dev can use, Pydantic validation |
| ORM | **SQLAlchemy 2.0** | Standard, works on SQLite and Postgres |
| Migrations | **Alembic** | The migration tool for SQLAlchemy; every schema change is a versioned file |
| Database | **SQLite** locally, **Postgres 16** in Docker | Zero setup to start, production-grade when deployed |
| Validation | **Pydantic v2** | Request/response schemas |
| Tests / lint | **pytest**, **ruff** | Fast; ruff runs in CI |
| XRPL | **xrpl-py** | Recommended by Ripple in the workshop |

Django would also work, but its ORM, admin and sync model add weight you won't use here. FastAPI is the better fit for an API that an agent and n8n call.

## 2. Database migrations (Alembic)

Run from `backend/`:

```bash
alembic upgrade head                                   # apply all migrations
alembic revision --autogenerate -m "add escrow table"  # after editing models/orm.py
alembic upgrade head
alembic downgrade -1                                   # undo the last one
```

Rules for the two of you:
1. Never edit a migration that is already on `main`. Add a new one.
2. Always review autogenerated files before committing.
3. If you both create migrations on separate branches you will get two heads. Fix with `alembic merge heads -m "merge"`.
4. The `audit_log` table is append-only. Do not add update or delete code for it.

## 3. GitHub steps

**One person (repo owner) does steps 1-4. Both do the rest.**

1. **Create the repo.** On github.com choose New repository, name `mandate`, set it to **Public**, do not add a README (we have one).
2. **Push the code.** From the project folder:
   ```bash
   git remote add origin https://github.com/<your-username>/mandate.git
   git push -u origin main
   ```
   Or with the GitHub CLI: `gh repo create mandate --public --source=. --push`.
3. **Add your teammate.** Settings, Collaborators, Add people, role **Write**.
4. **Protect `main`.** Settings, Branches, add a rule for `main`: require a pull request before merging, require the **CI** status check, require 1 approval (or 0 if time is very tight).
5. **Teammate clones.** `git clone https://github.com/<owner>/mandate.git`
6. **Branch per task.** Examples: `feat/policy-engine`, `feat/mandate-ui`, `feat/n8n-invoice-flow`. Keep branches short-lived, a few hours at most.
   ```bash
   git switch -c feat/policy-engine
   git add -A && git commit -m "Add daily cap check"
   git push -u origin feat/policy-engine
   ```
7. **Open a pull request** into `main`, let CI pass, have your teammate review, then **Squash and merge**.
8. **Sync often.** `git switch main && git pull` before starting new work, and rebase long branches on `main`.
9. **Track work.** Turn the MVP checklist in `docs/PROBLEM.md` into GitHub Issues and drag them across a Projects board (To do, Doing, Done).
10. **Split ownership to avoid conflicts.** Person A owns `backend/`, Person B owns `frontend/` and `n8n/`. Agree on the API contract first (`/docs` from FastAPI).

### Secrets
- Never commit `.env` or a wallet seed. `.gitignore` already excludes `.env`.
- Share test seeds privately, not in chat history that is public.
- If a seed is ever pushed, treat it as burned: make a new wallet. Deleting the commit is not enough.
- For CI secrets, use Settings, Secrets and variables, Actions.

### Hackathon submission
Before the deadline make sure the repo is public, `README.md` has run steps and a demo link, and the Participant Hub submission points to the final commit. Tag it: `git tag v1.0-submission && git push --tags`.

## 4. Local run

```bash
cp .env.example .env
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
alembic upgrade head
uvicorn app.main:app --reload          # http://localhost:8000/docs
PYTHONPATH=. pytest -q
```

Or everything in Docker: `docker compose up --build`.
